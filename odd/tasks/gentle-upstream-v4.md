## Ownership decision (no re-pin)

Pi stays owned by the nixpkgs pin, Gentle Shell by the native installer (which owns the `~/.pi/agent/settings.json` pin, preserved verbatim, and the `~/.pi/agent/npm` tree that `sync` reconciles), and Gentle AI by `packages/gentle-ai`. No repository file pins Pi or `npm:gentle-pi`, deliberately: a repo-owned pin of `npm:gentle-pi@4.0.0` would add a second writer over a runtime-owned file and open a window where the declared pin disagrees with the installed tree, and a `pi-coding-agent` overlay would make the flake shadow nixpkgs at the cost of `hash`, `npmDepsHash` and `modelData.hash` on every Pi release. Upstream on 2026-10-06: Pi v1.0.4 (nixpkgs master 1.0.3, the `main` pin 1.0.2), Gentle AI v4.0.0, npm `gentle-pi` 4.0.0. Consequence: reaching the newest Pi needs a nixpkgs update rather than a repository pin, and the Shell reaches 4.0.0 through GU-4.

## Engram plugin and engine pairing (found during GU-4, 2026-10-06)

`Gentleman-Programming/engram` is a monorepo with two independent release lines: the Go engine tagged `v*` (v2.1.0, v2.2.0, v2.2.1, v3.0.0, v3.1.0) and the Pi plugin tagged `pi-v*` (newest `pi-v0.2.0`, published to npm as `gentle-engram@0.2.0`). Comparing the plugin's `0.2.0` against the engine's `3.1.0` compares two different artifacts; `0.2.0` is the current plugin release, not a stale one.

The real gap is the engine. `packages/engram/package.nix` pins `2.0.0-rc.11`, a release candidate that the engine's own line has since passed. The `pi-v0.2.0` release note requires "Engram v3.0.0 or later for `expected_project` updates and deletes, `resume` registration of ended sessions, and isolated cross-project saves (`capabilities.isolated_session_registration`)".

Measured against the live profile rather than assumed:
- `GET http://127.0.0.1:7437/health` returns `{"service":"engram","status":"ok","version":"2.0.0-rc.11"}` with **no `capabilities` object at all**.
- `mem_update` and `mem_delete` **both succeeded** with plugin 0.2.0 against engine 2.0.0-rc.11. A scratch observation was created, updated to `revision_count: 2`, then hard-deleted. The declared `expected_project` dependency therefore does not break those two paths on a 2.x server in this configuration.
- The capability gate is required only on the satellite registration path, which fires when Pi saves to a project other than the active one. Its own error text is explicit: "Upgrade the Engram server to one advertising capabilities.isolated_session_registration: true in GET /health before saving to another project. No satellite session was registered." Cross-project memory saves therefore fail closed with guidance, and nothing is written silently.

- `mem_list_projects` fails with **HTTP 404** against engine 2.0.0-rc.11. That matches a second documented floor, recorded at v2.1.0: "Pi project listing needs an Engram server at least v2.1.0". The pinned `2.0.0-rc.11` sits below `2.1.0`, so the engine is behind two published floors, not one. `mem_stats`, `mem_current_project` and `mem_review` still work, and `mem_current_project` degrades `available_projects` to `null`.

Separate finding, unrelated to the plugin/engine pairing: `engram doctor` reports 8 checks with 6 ok, 1 warning and 1 error. The error is `sync_target_closed_space` with 9 findings — `cloud:system` 3199, `cloud:brain` 2521, `cloud:harness-civislend-analisis` 2491, `cloud:anonymizer` 620, `cloud:platform` 543, `cloud:documentation` 19, `cloud:secrets` 4, `cloud:downloads` 3, `cloud:avicente` 2 — 9402 unacknowledged mutations whose targets no configured pipeline can deliver, since `engram cloud status` reports cloud as not configured at all. The warning is `unowned_session_project` for session `manual-save`, whose safe next step is `engram projects rescue-ownership --project <name> --session manual-save` and which requires confirmation. `engram doctor` exits 0 while reporting `error`, so it must be read, not merely exit-checked. This store work needs its own decision and possibly its own task; it is not part of the plugin/engine pairing.

Consequence of the out-of-plan npm update: plugin 0.1.16 did **not** require `isolated_session_registration`; the gate arrived in 0.2.0. Bumping `gentle-engram` to 0.2.0 while the Nix engine stays at 2.0.0-rc.11 introduced the requirement. `resume` registration of ended sessions was not exercised and remains unverified.

Two coherent resolutions, neither taken, both needing explicit authorization:
1. Bump the engine pin in `packages/engram/package.nix` from `2.0.0-rc.11` to `v3.1.0`. That is its own repository source change, so its own ODD feature with TDD on, refreshed `hash`/`vendorHash`, the upstream `/v2` to `/v3` Go module path move, updated checks, native review, and a live SQLite backup of `engram.db` before any activation involving a schema migration.
2. Restore the pairing that matches the pinned engine by setting the versioned spec `npm:gentle-engram@0.1.16` in `settings.json`, mirroring the `gentle-pi` drift guard so `pi update` skips it. Note that `gentle-ai sync` manages `engram` as a component and may re-normalise it.
